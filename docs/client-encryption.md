# 客户端加密参考设计（密码学方案）

> 状态：参考稿，2026-11-25。只做方案研究、不写代码。对照 roadmap 第 19 项（客户端加密，P3，低优先级）。
> 定义：上传前在本机加密（内容 + 文件名），云端只存密文；密码不出本机；丢了密码文件永久打不开。
> 来源：rclone crypt 官方文档（rclone.org/crypt）、Cryptomator 安全架构文档（docs.cryptomator.org/security/architecture）、Air Explorer 文件加密页（airexplorer.net/en/file-encryption）。

## 一、三家方案对照

| | rclone crypt | Cryptomator（vault format 8） | Air Explorer（闭源） |
|---|---|---|---|
| 密钥派生 | scrypt（N=16384, r=8, p=1），密码（+ 可选第二口令作 salt）→ 80 字节密钥材料 | scrypt（cost 32768, block 8）从密码派生 KEK，再用 AES Key Wrap（RFC 3394）包裹随机主密钥 | 只公开“密钥由密码派生”，参数未公开 |
| 主密钥层 | 无。密钥直接由密码派生 | 有。两个 256 位随机主密钥（加密主密钥 + MAC 主密钥，CSPRNG 生成），存 `masterkey.cryptomator` | 未公开 |
| 内容加密 | NaCl SecretBox（XSalsa20 + Poly1305），64 KiB 一块，每块 16 字节认证 + 密文；文件头 8 字节 magic `RCLONE\x00\x00` + 24 字节随机 nonce，nonce 每块递增 | 每文件一个随机 32 字节内容密钥（存在加密文件头里）；内容分 32 KiB 块，每块 12 字节 nonce + AES-GCM 密文 + 16 字节 tag，AAD 绑定块号与头 nonce。旧组合 SIV_CTRMAC：AES-CTR + HMAC-SHA256 | AES-256，细节未公开 |
| 文件名加密 | AES-256 EME（ECB-Mix-ECB，Halevi-Rogaway 2003）确定性加密，逐段加密，PKCS#7 补到 16 字节倍数；base32 小写去 `=` 编码（兼容大小写不敏感的云）；文件名上限约 143 字符；目录名可选择加密或保留 | AES-SIV 确定性认证加密，父目录 ID 作 associated data（防跨目录移动）；超长文件名缩短存储（阈值 220 字符） | AES-256，文件名也加密；可按文件夹 / 账号开关 |
| 不加密的东西 | 文件长度（可推算 ±16 字节）、修改时间；无内容哈希（靠 Poly1305 认证） | 时间戳、文件数量、文件大小（32 KiB 粒度可见） | 未公开 |
| 换密码成本 | 全部重传（密钥直接由密码派生，改密码 = 改密钥） | 只重包主密钥，不用重传文件 | 忘密码 = 永久丢失，无恢复 |
| 开源 / 互通 | MIT 开源，格式公开，任何 rclone 都能解 | 开源，格式公开（vault.cryptomator JWT + masterkey.cryptomator JSON），第三方可实现 | 闭源，无公开格式；免费版能打开 Pro 加密的文件（格式不依赖许可证） |

## 二、rclone crypt 细节（最值得抄的部分）

- **分层思想**：crypt 不是一个驱动，而是一个包在任何驱动外面的加密层（`crypt remote` 包 `remote:path`）。上传时加密、下载时解密，中间驱动完全不知道自己在传密文。ZyDrive 照这个思路做，就不用给六个驱动各写一套。
- **内容格式**：文件与密文 1:1，头 32 字节（8 字节 magic + 24 字节 nonce）+ 64 KiB 一块；1 MiB 文件开销约 0.03%。64 KiB 是实测的最佳块大小（再小认证开销大，再大缓存效应变差）。
- **文件名格式**：同名必同密文（否则云端找不到文件），但同前缀的文件名加密后没有公共前缀（EME 宽块模式的性质）。`base32` 而不是 `base64`，是为了大小写不敏感的云（Dropbox、OneDrive、Windows）也能用；OneDrive、Dropbox 这类按 UTF-16 计长度的云可用 `base32768` 缩短。
- **弱点（不要学）**：配置文件里的口令只是轻度混淆（AES-CTR + 固定密钥，IV 明文存），不是加密；官方文档自己写明“不安全，除非给整个配置文件再加一层加密”。ZyDrive 不能这样存——口令派生的密钥材料必须进已有的 master.key 加密体系。
- **盐**：salt 是可选的第二口令（password2），不存云端，用户自己记；不用 salt 时用内置固定值。scrypt 让字典攻击不现实，但官方仍建议始终用 salt。

## 三、Cryptomator 细节（最值得抄的部分）

- **主密钥层**：随机主密钥 + 口令派生 KEK + AES Key Wrap，是它比 rclone 高明的地方。换密码只需重新包裹主密钥，云端文件一个字节都不用动；rclone 没有这层，换密码 = 全部重传。
- **vault 结构**：根目录两个文件——`vault.cryptomator`（JWT，HS256 签名，含 format、shorteningThreshold、cipherCombo、随机 UUID）+ `masterkey.cryptomator`（JSON：scrypt 参数 + 包裹后的两个主密钥 + versionMac 防降级攻击）。没有中央索引文件，每个文件自带解密所需的一切（除密钥外），坏一个文件不连累全库。
- **文件名**：AES-SIV 是确定性认证加密——同一个名字在同一个目录里总是同一个密文，但不同目录里的同名文件密文不同（父目录 ID 进了 associated data），移动文件跨目录会被发现。目录结构本身也被混淆（每个目录一个随机 ID），云端看不到真实层级。
- **内容**：每文件独立随机内容密钥，一文件一密，改一个文件只重传那一个文件的密文；块级认证（GCM tag / HMAC）让静默篡改能被发现。

## 四、Air Explorer（能参考的很少）

- 公开信息只有：AES-256、内容 + 文件名、上传前本机加密、密码派生密钥、密码不出本机、可按文件夹 / 账号开关、免费版能打开 Pro 加密的文件、忘密码永久丢失。
- 没有公开的格式文档，意味着它的密文只能用它自己的软件解。参考价值在于产品形态（按文件夹开关、免费版可解密保底），不在于密码学实现。

## 五、给 ZyDrive 的建议（参考设计）

按 Cryptomator 的分层抄骨架，按 rclone 的包装层抄结构，算法用 Go 标准库能直接拿到的。

1. **分层**：随机主密钥（CSPRNG 生成，256 位加密 + 256 位 MAC）→ 口令经 scrypt 派生 KEK → AES Key Wrap（RFC 3394）包裹主密钥。换密码只重包主密钥，不重传。主密钥密文与 scrypt 参数存在云端固定位置（如加密根目录的 `zy-drive-vault.json`，仿 masterkey.cryptomator），格式写死版本号，留升级路径。
2. **内容**：AES-256-GCM 分块（Go 标准库 `crypto/aes` + `cipher.NewGCM` 就有，不用引第三方）：32 KiB 一块，12 字节随机 nonce，AAD 绑定块号与文件头 nonce；每文件一个随机内容密钥，存在加密文件头里。不要用 ECB；nonce 绝不重用；不要自己发明模式。
3. **文件名**：AES-SIV 确定性加密（`golang.org/x/crypto/siv`），父目录 ID 作 associated data；超长做 shortening（阈值抄 220 字符）。rclone 的 AES-EME 也可以，但 Go 没有标准库实现，要自己写，不如 SIV 现成。
4. **包装层**：做成 Provider 外面的加密包装（像 rclone crypt remote），不是每个驱动各写一套；加密只在指定的 Mount / 目录上开启，加密目录与非加密目录不混在一个 Mount 里（rclone 的教训：混用会把未加密文件也当密文读）。
5. **密钥存哪**：复用 ZyDrive 已有的 master.key 加密体系（PBKDF2 + AES-256-GCM）存 KEK 相关材料；**加密口令必须与登录口令分开单独设**，绝不存明文，绝不进数据库备份，绝不随同步任务下发到 Agent 以外的地方。
6. **Agent**：定时同步跑在 Agent 上时也要加解密，口令材料随加密配置包一起下发——这意味着 Agent 服务器上也有口令材料，部署文档里必须写明这个风险，由用户自己决定是否在服务器上放加密任务。

## 六、代价清单（做之前必须写进 UI 文案）

- 丢密码 = 文件永久打不开，没有找回，没有后门。
- 加密后云端搜不到内容、缩略图、文件预览、去重全部失效——但本地索引可以把其中大部分补回来（见第八节），失效的是云厂商提供的服务端能力，不是 ZyDrive 自己的能力。
- 文件名变长（base32 后约 1.6 倍），OneDrive 400 字符路径限制更容易触顶——见第七节，有四档办法。
- 同步比较不能再靠内容哈希（云端只有密文哈希），改大小 + 时间，或对密文做哈希。
- 加密与非加密内容不能互相复制（跨 Mount 复制要先解密再加密，走本机内存，不走服务端直传）。

## 七、文件名变长怎么办

加密后文件名一定变长，问题不在“变长”本身，而在各家对长度的上限不同：

- 多数云与本地文件系统：单个文件名限 255 字节（UTF-8）；Drime 同样是 255 字节。
- OneDrive：整条路径限约 400 字符，目录层级深 + 加密名一叠加最容易触顶。
- rclone 的实测安全线：明文名 ≤143 字符时，标准模式在任何云上都不会超限。

四档办法，按推荐顺序，组合使用：

1. **按云选编码**（零成本，rclone 现成的 `filename_encoding` 思路）：
   - 默认 base32：全小写、大小写不敏感的云都能用，膨胀约 1.6 倍。
   - OneDrive、Dropbox 这类按 UTF-16 计长度的云用 base32768：每个字符带 15 位信息，膨胀只有约 1.07 倍，几乎不长——但它是非 ASCII 字符，Drime、S3 这类按 UTF-8 字节计长度的云用了反而更长（一个字符 3 字节），所以编码必须按云选，不能全局统一。
   - 大小写敏感的云可用 base64：膨胀约 1.33 倍，比 base32 短。
2. **Shortening（Cryptomator 的做法）**：超过阈值（Cryptomator 用 220 字符）的加密文件名，不直接当文件名用，改用一个短的派生名，完整密文名单独存一个小映射文件里，打开时再查回来。代价是每个超长文件多一个映射文件、列表时多一次查询；好处是再长、再深的路径都不会触顶，是兜底方案。
3. **目录名不加密**（rclone 的 `directory_name_encryption=false`）：目录名通常不敏感，留明文能省下整条路径上很大一截预算，代价是目录结构对云厂商可见。这是性价比最高的折中。
4. **文件名加密可关**（rclone 的 `filename_encryption=off`）：只加密内容，文件名明文，长度零膨胀。内容加密才是主防护，文件名加密是纵深防御；对路径深、名字长的用户，关掉文件名加密比反复触顶更实用。做成按加密目录开关，默认开。

推荐组合：默认 base32 + 目录名可选择不加密 + 超长自动 shortening；OneDrive、Dropbox 自动切 base32768；文件名加密可按目录关闭。

## 八、搜索、缩略图、去重怎么做（本地索引）

不用每次下载。正确做法是**在本地维护一套解密后的索引**，云端是密文，本地输入口令后看到的是解密后的内容：

- **文件名搜索、浏览**：完全不用下载。列目录时文件名在内存里解密，搜索直接跑在解密后的名字上（可以先缓存在本地数据库里，秒出结果）。
- **按名 + 大小去重**：不用下载。文件长度是不加密的（rclone 是 ±16 字节内可见，Cryptomator 是块粒度可见），列表时直接拿得到。
- **按内容哈希去重**：哈希只算一次，算完进索引。最便宜的时机是**上传时**——那时明文就在手里，顺手算个哈希、生成缩略图、抽个全文关键字，零额外下载。别人传上来的、以前传的，第一次下载/打开时算一次并缓存，之后不再下载。
- **缩略图**：同理，上传时或首次打开时生成，缓存在本地。缩略图本身是明文图片，必须和索引一起加密存放（复用 master.key 体系），不能明文躺在磁盘上。
- **全文搜索**：内容在上传时或首次建索引时抽成关键字存本地；没建过索引的文件要搜全文，必须先下载一次（流式解密、抽完即弃，明文不落盘）。
- **索引放哪**：本地 SQLite（ZyDrive 已有 `internal/cache` 这层，直接扩展），全部内容用 master.key 加密存放。索引是本机私有的，不上传。
- **换设备 / 重装**：索引丢了要重建——文件名搜索重建很快（只拉目录列表解密），内容哈希/缩略图/全文要重新下载一遍才能建回来。进阶做法是把索引本身加密后当一个小对象放云端（随主密钥一起保护），换设备时下载索引即可；代价是每次改动都要更新索引对象（写放大），多人同时改会冲突。v1 先做本地索引，云端同步索引以后再定。
- **加密文件跨云复制反而更方便**：同一套口令、同一套格式时，密文可以直接从一个云搬到另一个云，不用解密再加密（服务端直传也行），明文全程不出现。这是加密后少数几个变简单的事。
- **仍然做不到的**：云厂商提供的搜索、预览、分享链接里的在线预览——密文在云端，厂商看不懂；分享加密文件给别人，对方也要装 ZyDrive + 拿口令才能解（Air Explorer 的加密分享就是这个做法）。

## 九、待决策与未解决问题（2026-11-25 复核）

前面八节是“抄谁、怎么抄”；这一节是复核时发现的、前面没覆盖的问题。排期 P3 立项时逐项定。

1. **格式：自研还是兼容 Cryptomator**：自研格式自由，但只能 ZyDrive 解；直接采用 Cryptomator vault format 8，则用户能用 Cryptomator 官方客户端打开同一个 vault，互通但受其布局约束（rclone crypt 格式同理）。默认倾向自研（我们的 Mount / 同步模型与 vault 目录结构不完全一样），但格式版本号要从第一天写死，留好“以后能否兼容”的口子。
2. **换格式的迁移**：算法升级（比如以后换更强的 KDF）= 全库重加密，需要旧口令 + 新口令 + 双倍空间 + 断点续传。迁移工具要作为功能的一部分排期，不能事后补。
3. **主密钥备份**：主密钥是随机的，不是由口令算出来的——vault 配置文件（包好的主密钥）丢了或坏了，有口令也解不开。建 vault 时必须强制导出一份恢复文件（离线保存，打印或存 U 盘），并在 UI 里提醒。只靠云端那一份是不够的。
4. **恢复口令**：无恢复是设计（丢口令 = 丢数据），但对普通用户太吓人。可选方案：建 vault 时生成一组恢复码（第二套 KEK 包裹同一主密钥），用户打印保存；不用就不存在，存在也不影响主口令。这是 BitLocker 恢复密钥的思路，Cryptomator 没有，值得抄。
5. **口令强度与解锁速度**：scrypt 参数是安全与速度的 trade-off（Cryptomator N=32768，rclone N=16384），定在格式里；解锁一次的耗时在手机上也不能太久。口令至少 12 位（Air Explorer 的要求），弱口令要警告，强度计要做。
6. **密码输错要立刻发现**：解锁时先解包主密钥，解包失败立刻报“密码不对”，不要等到列目录 / 下载时才出乱码。rclone 的体验就是后者——文件名解出来是乱码，用户分不清是密码错了还是文件坏了。
7. **Nonce 与密钥分离**：每文件内容密钥独立；块 nonce 用块号计数器（确定性、不重用、不占存储），不要随机；内容密钥、文件名密钥、MAC 密钥三者分离，绝不一钥多用；随机数只用 crypto/rand。
8. **同步引擎的四个坑**：
   - 密文大小与明文大小不是 1:1（每块 16 字节认证 + 头），小于一块的改动可能不改变密文大小，比较时 mtime 是主要信号，时钟偏差会误判；
   - 改名 = 文件名重加密 = 云端看到删 + 建，Mirror 模式要靠本地索引的内容哈希认出是改名而不是删了重传；
   - 断点续传必须对齐密文块边界，中断后从块续传，不能从文件中间续一个流式密码状态；
   - 0 字节明文加密后仍有头（几十字节），大小比较要扣掉固定开销。
9. **首次建索引的成本**：已有加密库（比如 Drime 上几百 GB）第一次建内容索引要把文件都下载一遍解密算哈希，必须是后台可选任务、带进度、可暂停，不能静默自动跑。
10. **记住口令**：提供“记住口令”（存系统钥匙串 / master.key 加密）是方便，但威胁模型变了：拿到设备 = 拿到文件。必须做成显式 opt-in，UI 写明风险；Agent 上则是不记口令、每次随配置包下发。
11. **解密永远免费**：即使加密功能本身以后放 Pro，解密必须免费（Air Explorer 同款做法）。否则用户停付费就打不开自己的文件，等于数据被付费墙绑架。已写进 `docs/monetization.md` 第 6 节。
12. **内存与日志**：密钥只放内存，用完清零（Go 里尽量做）；日志绝不打印口令、密钥、明文文件名；崩溃报告要过滤。
- 加密口令与 Mount 凭证是两套东西：换网盘 Token 不影响加密，换加密口令要重包主密钥（不用重传文件，但旧口令的备份必须留着直到重包完成）。
